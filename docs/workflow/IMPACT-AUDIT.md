# 影响核查：避免默认零分

这是现行 v2.4 的执行清单，不改变政策、评分公式、L1 复核门槛或批准契约。规则以 [EDITORIAL-STANDARD](EDITORIAL-STANDARD.md) 的 CONF/EVID/IMP 为准；结构见 [REVIEW-CONTRACT](../data/REVIEW-CONTRACT.md)。

## 先区分状态

- **未评估**：没有逐项核查；不能声称没有影响。
- **已检查，证据不足计分**：写清候选后果、未纳入理由和缺口；不是实测零影响。
- **实测中性**：有基线、结果和证据支持 severity=0；不能用空数组代替。
- **有方向性后果**：按原规则给 severity，并用原公式算 impactIndex。两者不是同一个数。

例如：单一维度 severity=+1、B 证据、一类受众、immediate，指数为 round(1/3+1+0.5)=2。L1 可以有非零影响；不人为维持整批为零，也不为了消除零分统一加分。

## 每条事件的操作清单

1. 冻结事件、来源、原 review、run、policy 和证据截止日；明确是当前联网补证还是复读历史存档。复读存档不能更新来源 accessedAt 冒充重新访问网页。
2. 阅读每个完整来源，把提及的后果逐项列入工作区取舍表。模板只生成待填字段，不生成 `not_found`、severity 或完成判断。
3. 对五个影响维度逐一检查；每项候选记录：原文/定位、信息起源、基线→结果、观察日期、受众、include/exclude/unresolved 及理由。未解决项保留未知，不变成实测零。
4. 区分当下可用、逐步推出、申请/计划、采用、规模、跑分与收益。可靠当事方对其实际访问动作的直接说明可按 EVID-03 支持 B；不能一律增加“必须有外部用户成功使用”条件，也不能把任意产品公告自动算成已观察影响。
5. 先判断是否有方向，再判断是否实质改变。+1 不要求先达到 +2 或 L2；+2 需要具体实质变化证据。受众按角色去重，持续性只按有证据的观察期。
6. 区分事故和后来披露：此前损害不能算成通报造成的后果。需要其他节点身份时先给出有界去重和身份方案，不为凑分新增、改日期或合并旧 URL。
7. 纳入的影响写入公开 claim、impacts 和同序 review.impactBasis；其余取舍保留在工作区。保留事件首次 publishedAt。新版本重新复核并按 PUB-01 请求精确人工批准，不沿用旧批准。
8. 汇总整批后检查异常模式。全部零分可以合理，但须能逐项解释；独立复核时同时看来源和取舍，不能仅验证数组为空或“有公告”。按现行 REVIEW-01 决定独立复核要求，不把实验门槛冒充现行 MUST。

## 辅助风险报告（只读，不阻断）

```bash
python3 -B scripts/report_impact_batch.py governance/runs/<实际批次>.json
```

报告提示整批空影响、重复理由、缺理由、“已找到影响却未录入”和可能误用独立采用门槛的情况。提示不证明事件分数有错，也不自动加分、生成事实判断、签发审核或批准。报告失败应先修复输入，不能把无报告当成无问题。

回归测试：`python3 -B -m unittest discover -s tests -p 'test_editorial_impact_batch.py'`。合成样例不进入治理证据。

## 未发布实验与生产规则的边界

此前 `impact_audit.py` 强制门禁及 rollout 快照草案留在未发布工作区，本次不包含，也不由生产 validate_all 加载。它们不是额外历史豁免，不表示 238 条内容已审计，不要求批准新增 impactAuditDigest。
