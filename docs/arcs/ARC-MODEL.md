# EpochArc 专题叙事标准 v2.4

规则边界：[EDITORIAL-STANDARD](../workflow/EDITORIAL-STANDARD.md) ARC-01、LANG-01/02。结构继承现有构建器，新增审核使用 [REVIEW-CONTRACT](../data/REVIEW-CONTRACT.md)。

## 1. 定位

Arc 将已发布事件组织成可阅读、可辩论的解释线索，不是新闻堆叠，也不是为了“锋利”而制造立场。

合格选题须有：

- 明确问题或可检验论点。
- 足够的已发布事件支持。
- 能指出反例、限制或替代解释。
- 判断力度不超过证据。

允许编辑解释，但应区分事实、归因与推测。中立不等于不作判断；有立场也不等于可以忽略反证。

## 2. 常见结构（SHOULD，不限制新结构）

| 结构 | 目标 |
|---|---|
| 技术演进 | 解释方法、约束与选择如何演化 |
| 主题线索 | 围绕安全、治理、开放性等跨事件问题 |
| 社会变化 | 从受影响人群的可观察行为组织事件 |
| 竞争路线 | 比较不同方案的证据、收益和限制，不预设赢家 |

不要求每章刻意反直觉，也不要求把仍有争议的问题写成确定答案。

## 3. MUST：数据结构

唯一编辑源 `content/arcs/*.json`；`data/arcs.json`、`arcs/{id}/index.html` 是构建输出。

每条含 id/title/subtitle/abstract/chapters/conclusion/status/editorial；文本为完整 en/zhHans。

- 3–6 章，每章 id/title/narrative/anchorEvents/keyInsight。
- 每章 2–5 个不重复的已发布锚点事件。
- 全文至少 5 个不同锚点事件。
- 最晚与最早事件年份差至少 3，沿用当前机械口径；不是用单月合集冒充长期演变。
- relatedArcs 不能自引、重复或引用未发布专题。
- 日期范围、分类和覆盖数量从锚点派生，不维护第二套数字。

## 4. MUST：论证与证据

- 每章有明确的论点或问题；可以论点先行，不受事件 summary 首句事实模板约束。
- 用锚点中的事实支持解释，不把锚点链接当成对所有新判断的兜底引用。
- 新增重要事实先按事件事实标准核实；新增重要解释在 review.evidence 中记录摘录、来源、章节/论点标识。
- 至少处理一个实质反例或替代解释，review.counterEvidence 记录检索结果；找不到时说明已查范围，不能虚构反方。
- 结语可以给出有限结论或尚未解决的问题，不强制预测市场赢家。
- 同一事件在不同 Arc 可以有不同解释，但不能出现相互冲突的未经说明的事实版本。

## 5. 双语与文风

中英文共享事实/主张台账。允许先写任一语言或并行写作；不得强制“中文不能看英文”，也不得强制“英文永远为准”。最终核对主体、数字、时点、因果、限制和不确定性，不要求逐句镜像。

建议英文 abstract 40–60 词、章节 narrative 100–200 词、conclusion 60–100 词；中文按自然信息量调整。这些是 SHOULD，不是牺牲事实边界的硬字数。

避免空洞自我介绍和营销语言。可用主动或被动句，以责任主体明确为先；不得为避免被动语态将“validated”自动改成更强的“proved”。

## 6. 复核与发布

1. 检查全部锚点为 published，章节结构与派生元数据正确。
2. review.eventIds 覆盖所有锚点；inputsDigest 绑定锚点及其公开来源，防止引用内容已变而复核仍称有效。
3. review 记录 changeReason/counterEvidence、证据、双语核对、操作者及实际日期。
4. 精确版本人工批准，运行统一校验、测试、构建。
5. 本地检查 TOC、事件链接、canonical/hreflang、两种语言及样式；生成页面不手改。
6. 无明确授权不 push。事件或来源改变时，重新检查受影响章节并更新对应 review/approval。

程序可检查引用与结构，不能证明论点有说服力或因果成立；这部分由证据复核负责。
